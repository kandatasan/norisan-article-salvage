■ 1. 制作ルートは1本だけ
サルベージ、リライト、新記事でルートを分けない。

ユーザー指示
→ 対象記事・検索意図・一次情報を確認
→ 現在のWordPressを確認
→ 必要な最新情報・サジェスト・写真を確認
→ 完成稿を作成
→ GitHub mainを確認
→ 作業専用ブランチ
→ 必要ファイルを追加・更新
→ Pull Request
→ 差分・対象・安全条件を監査
→ 安全ならmainへマージ
→ GitHub Actions
→ 監査ログ
→ WordPress反映確認
→ 完了報告

「サルベージだから別ルート」「新記事だから別ルート」は禁止。
違うのは、対象記事がWordPressに存在するかと現在のstatusだけ。

■ 2. 新規・既存
対象なし：新規。status=draft。勝手にpublishしない。
既存draft：draftのまま更新。post ID・slugを勝手に変えない。
既存publish：ユーザーが更新を明示した場合はpublishのまま更新。勝手にdraftへ戻さない。

■ 3. 事実確認の優先順位
1. 現在のWordPress実体
2. 現在のGitHub main
3. 最新のユーザー提供ファイル
4. 過去の記録・会話・Memory

古いスクリプト名や旧ルートを記憶から復活させない。
現在のmainに実在するworkflow・script・package形式だけを使う。

■ 4. 記事内容の情報源優先順位
1. 今回のユーザー発言
2. 最新WordPress実体・エクスポート
3. ユーザー提供の写真・一次資料
4. 旧記事に残る一次体験
5. つりくえ！各ルール
6. 公式・公的な一次情報
7. サジェスト・検索結果
8. その他Web情報

一次体験の事実・感情はAIが補完しない。

■ 5. GitHub安全ルート
使用リポジトリ：kandatasan/norisan-article-salvage

必須：
・main確認
・作業専用ブランチ
・変更はブランチのみ
・PR作成
・差分確認
・対象post / slug / status / media確認
・安全ならマージ
・Actions確認
・監査ログ確認
・WordPress実体確認
・その後に完了報告

禁止：
・mainへ直接書き込み
・差分未確認でマージ
・post / slugを推測
・Actions成功だけで完了扱い
・WordPress未確認で反映完了と言う
・認証情報の表示

■ 6. GitHub実装名は固定しない
特定のPython名、workflow名、package名を永久の正解として情報源に固定しない。
実行時に現在のmainを確認する。
共通レールが壊れている場合も、branch→PR→監査→mainの安全ルート内で修正する。

■ 7. WordPress更新
必要な項目だけ変更。
既存記事のpost ID / slug / status / featured mediaを無関係な作業で変えない。
写真だけ追加する場合、古い本文全体で上書きしない。

■ 8. 実行許可
「GO」「進めて」「次いこー」「下書きまで」「反映して」「リライトして」「よろしく」など実行が明確なら、完成稿だけ出して終了しない。
安全に進められる限りWordPress反映確認まで進める。
毎回許可を取り直さない。

停止条件：
・対象記事を一意に特定できない
・slug / post ID不一致
・別記事破損の恐れ
・人間のWP修正を上書きする恐れ
・写真の権利や対応が不明
・重複記事の恐れ
・PR差分が想定外
・WP実体が事前確認から変化

■ 9. 完了条件
最低限：
・PR差分OK
・mainへ安全に反映
・Actions成功
・post ID確認
・slug確認
・status確認
・title確認
・必要ならfeatured media確認
・WordPress本文確認
・対象外記事を変更していない
・監査ログ確認

新規の基本安全条件：status=draft
既存の基本安全条件：statusが意図せず変わっていない

■ 10. 完了報告
短く、
・何をしたか
・title
・slug
・post ID
・status
・写真
・監査結果
・公開したか
を伝える。

■ 11. 編集の最上位理念：追体験できるSEO（2026-11-01追記）
検索した人が必要な情報を見つけながら、筆者と一緒にその場所・場面を経験した気分になれる記事を目指す。
「SEO情報は裏で支える。表では遊ぶ。」の具体化であり、一次体験・正確性・既存の安全ルートより優先して事実を創作するものではない。

制作時の基本動線：
・読者の疑問・検索意図を把握する
・実際の体験に沿って、場面→発見→本人の反応→必要な実用情報→次の場面へ運ぶ
・実際に回った順番に意味があるならその順序を生かす
・検索者が急いで知りたい料金・場所・所要時間等は見つけやすく整理する
・写真は飾りではなく、その場にいる感覚を補強する位置に置く
・驚きやツッコミは本人が語ったもの・資料で裏付けられるものを生かし、AIで捏造しない

完成の判断：
「何があるかを説明しただけ」で終わっていないか。
「読者は今どこで何を見ているか」「筆者は何を発見し、どう反応したか」が自然に伝わるか。
読者が行く・食べる・釣る・乗る際の判断にも役立つか。

細かな文章リズム、WordPressの同一段落内改行と新ブロックの使い分け、追体験の品質監査は「01_つりくえ_編集文章ルール」の2026-11-01追記を参照する。

■ 12. 改訂版の採用・実例
基準となる既存記事：松江フォーゲルパーク（https://tsurikue.com/matsue-vogel-park/）。
今回の実践例：トムとジェリー展（WordPress post ID 4282、2026-11-01時点の追体験型本文）。
実例は文章のコピー元ではない。「発見→本人の反応」「自然な小さなツッコミ」「読者が順に体験する動線」を再現するための参照例とする。
施設・釣り・グルメ・ドライブ・クルマなど、題材ごとに最適な順番・情報量を調整し、毎記事を同じ構文にしない。

最重要：
確認→完成稿→GitHub branch→PR→差分監査→main→Actions→WordPress→最終監査。
