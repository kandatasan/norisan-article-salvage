調査・研究実装：2026-10-20 JST。

## ここまでの成果

前段 v0.8 で、428の河川名IDについて魚類・底生動物・鳥類・植物の**原本にある掲載名を全件**検索できるSQLiteを作成し、今回 v0.9 ではそのデータを軽量な静的配信形式へ変換した。

| 研究データ | 実測 |
|---|---:|
| 河川名ID（10桁河川コードなしも含む） | 428 |
| 独立した分類窓（河川×4分類） | **1,712** |
| 調査原本の河川別掲載名の組み合わせ | **254,574** |
| 紐付く過去の河川別調査文脈 | **553,351** |
| 記録がまだない分類窓 | 456 |
| 地方別の圧縮ZIP | 9 |
| 全地方の圧縮データ合計 | 約3.95 MB（ZIP9本の合計・独立した保存形式） |

254,574は分類学的な生物種数や新しい観察件数ではない。「河川名ID×生物分類×資料記載名」を元の表記のまま保持した**重複し得る掲載名数**。554千に近い文脈データも実際の観察個体数ではない。

**生物記録は河川名があるものだけを収録。** 水系全体しか分からない記録を支流に配分しない。コードがなくても河川名・水系・調査機関を識別IDに使用し、同名河川の混同があるものは保留する。希少種の正確な採集位置・座標は付けない。

## 読者が使う想定UI

`都道府県 → 水系 → 河川 → 生物4分類`

- 都道府県：全47件の選択肢を用意。研究段階で水系と照合できたのは28都道府県。
- 水系：公的資料により県との関係が示される**80件の入口**。ここに生物の一覧は設けない。
- 河川：対象水系に属すると公式生物調査に記載された河川名を一覧で見せる。都道府県内の所在地が確定した川とは限らないため、県・水系の表示関係と川の実位置を混同しない。
- 生物：魚類・底生動物・鳥類・植物の4枠。選んだ分類の掲載名・記録回数・年度・原資料URLを読み込む。生物名絞り込みと「さらに35件表示」に対応。

旧 v0.7 のUIでは各分類の掲載名サンプルは2件まで。**今回のUIは選択河川・選択分類に属する掲載名を全件扱う**。全国の生物名25万件を最初のHTMLへ埋め込まず、ユーザーが選んだ分類のJSONだけを遅延取得する。

検索画面は **iframeを使わない**。サーバー上へJSONを展開して、HTMLと同一オリジンで配信する前提。

## 試作品の開き方

GitHubから `outputs/river_atlas_static_preview_v09.zip` を取得・解凍し、そのフォルダーをPCのターミナルで開き、次を実行。

```bash
python -m http.server 8000
```

ブラウザで `http://localhost:8000/` を開く。都道府県を選択し、確認済み水系・河川へ進み、4分類をクリックする。

**注：** `file://` からindex.htmlを直接開くと、ブラウザがローカルJSONの読み込みを拒否する場合がある。Pythonの簡易HTTPサーバーはローカル検証用であり、外部公開・WordPress配信ではない。

## データの制約・未実装

1. 過去の調査資料の掲載名。記載例には種名だけでなく属名・科名なども含まれ、厳密な現在の分類名・種数ではない。
2. 過去の記録であり、現在の生息・出現場所・個体数を保証しない。「調査記録なし」も不在の証明ではない。
3. 県の資料に水系が掲載された場合でも、その支流の全てが県内にあるとは限らない。正確な流路や合流関係も個別検証が必要。
4. 入手済み原本URLは各名に保存。元データの利用条件・出典表示など**公開前の法務確認は未完了**。商用利用可否を推測で決めない。
5. GitHub ActionsはHTTPリクエスト・JS構文・ZIP・SQLite・件数保存を検証。PC/スマホ実機のクリック操作・パフォーマンス計測は別途必要。
6. 生物名の見た目や振り仮名、同物異名の統合は未実施。現在の「254,574件」を種数に読み替えてはいけない。

**公開・WordPress下書き反映には改めて利用者の承認を得る。研究ブランチのまま運用。**
